# 추적성 규칙

## 1. 목적

본 규칙은 블록체인 기반 정품 인증 서비스 Requirements Repository에서 산출물과 추적 대상 간의 관계를 정의하고, 그 관계를 기록하는 방법(`based_on`)과 변경 영향을 확인하는 방법을 정의한다.

추적 대상의 ID 형식과 번호 부여 기준은 `규칙/01-ID 스키마.md`를 따른다. 본 규칙은 ID 간의 **관계**만 다룬다.

---

## 2. 추적 체인

Repository의 추적성은 `ACTOR-###`를 뿌리로 하여 다음 순서로 파생된다.

화살표(↓)는 상위 근거에서 하위 산출물로 파생되는 방향이다.

```
         ACTOR
        ↓     ↓
  PERSONA     STORY      POLICY
 (종속 분류)     ↓          ↓
                └────┬─────┘
                     ↓
                     BR
                     ↓
                     PR
```

`PERSONA`는 `STORY`의 근거가 아니라 `STORY`가 선택적으로 참조하는 보조 자료이므로 다이어그램에서 `STORY`와 연결하지 않았다(표 3행 참조).

같은 내용을 파생 관계 목록으로 나타내면 다음과 같다. `A → B`는 "A를 근거로 B가 도출된다"는 뜻이며, `based_on`은 이 화살표의 반대 방향(B가 A를 가리킴)으로 기록한다.

| 순서 | 상위 근거 | → | 하위 산출물 |
| --- | --- | --- | --- |
| 1 | `ACTOR` | → | `PERSONA` |
| 2 | `ACTOR` | → | `STORY` |
| 3 | `PERSONA` | → | `STORY` (선택, 보조 참조) |
| 4 | `STORY` | → | `BR` |
| 5 | `POLICY` | → | `BR` |
| 6 | `BR` | → | `PR` |

| 대상 | ID | 정의 문서 |
| --- | --- | --- |
| Actor | `ACTOR-###` | `BR/05-역할.md` |
| Persona | `PERSONA-###` | `BR/06-페르소나.md` |
| User Story | `STORY-###` | `BR/07-고객여정/{Actor}/04-유저스토리.md` |
| Policy | `POLICY-###` | `BR/08-정책.md` |
| Business Requirement | `BR-###` | `BR/09-요구사항.md` |
| Product Requirement | `PR-###` | `PR/` |

고객 저니, 유저 시나리오, 유저 플로우는 추적 대상이 아니며(ID 스키마 §13) 스토리를 도출하는 근거 자료로만 사용한다.

## 3. 관계 정의

관계는 **하위 항목이 상위 근거를 가리키는 단방향**으로만 기록한다.

| 하위 항목 | 상위 근거 | 필수 여부 | 기록 방식 |
| --- | --- | --- | --- |
| `PERSONA-###` | `ACTOR-###` 정확히 1개 | 필수 | Persona 제목에 Actor ID 표기(ID 스키마 §11) |
| `STORY-###` | `ACTOR-###` 정확히 1개 | 필수 | 스토리에 Actor ID 표기(ID 스키마 §13) |
| `STORY-###` | `PERSONA-###` | 선택 | 이용 패턴·Pain Point를 설명하는 보조 참조 |
| `BR-###` | `STORY-###`, `POLICY-###` | 하나 이상 필수 | `based_on` |
| `PR-###` | `BR-###` | 하나 이상 필수 | `based_on` |

### 관계 기준

* `POLICY-###`는 상위 추적 대상을 별도로 갖지 않는다. 정책의 근거는 정책 문서의 책임 범위에서 관리한다.
* BR은 STORY와 POLICY 중 하나 이상을 근거로 삼는다. 하나의 BR이 여러 STORY·POLICY를, 하나의 STORY·POLICY가 여러 BR을 근거로 연결될 수 있다(N:M).
* PR은 BR만 근거로 삼는다. PR이 `STORY-###` 또는 `POLICY-###`를 직접 참조하지 않는다. STORY·POLICY까지의 경로는 PR이 근거로 삼은 BR을 거쳐 확인한다.
* BR의 Actor는 근거로 삼은 STORY의 Actor로 확인한다. BR이 정책만을 근거로 하는 경우 Actor는 필요할 때 `based_on`에 `ACTOR-###`를 함께 기재한다.
* ID가 없는 Business Context 문서(서비스 개요, 서비스 배경, 범위, 이해관계자 등)는 `based_on` 대상이 아니다. 요구사항의 근거가 이 문서의 내용뿐이라면 해당 내용을 STORY 또는 POLICY로 먼저 정의한 후 참조한다.

## 4. `based_on` 사용 기준

* `based_on`은 **이 항목이 무엇에 근거해 도출되었는가**를 나타낸다.
* `based_on`은 하위 항목에만 기록한다. 상위 항목에는 하위 항목 목록(역참조)을 작성하지 않는다. 역방향 관계는 `based_on`을 검색하여 확인한다(중복 관리 방지).
* ID 번호나 문서 위치로 관계를 표현하지 않는다(ID 스키마 §2).
* 근거는 실제로 요구를 도출한 상위 항목만 기재한다. 관련성이 낮은 항목을 참고용으로 나열하지 않는다.
* 근거를 확인할 수 없는 항목은 작성하지 않고 Open Issue(`OI-###`)로 등록한다.

### 표기 형식

`based_on`은 ID 스키마 §9에 따라 ID와 명칭을 함께 표기하고, 여러 개는 쉼표로 구분한다.

```
STORY-003 — 진위 조회 결과 확인, POLICY-005 — 조회 결과 유형
```

### 기재 위치

BR과 PR은 다음 열을 가진 표로 관리한다.

| ID | 요구사항 | based_on | 비고 |
| --- | --- | --- | --- |
| BR-### | 요구사항 내용 | `STORY-###`, `POLICY-###` | |
| PR-### | 요구사항 내용 | `BR-###` | |

* `비고`에는 요구사항이 분리·통합된 경우에만 관련된 이전 ID를 기재한다(§6 참조).
* PR이 여러 파일로 나뉘더라도 열 구성은 동일하게 유지한다.

## 5. 추적 완결성 기준

다음 항목을 추적성 검증의 기준으로 사용한다.

| 검증 항목 | 위반 시 조치 |
| --- | --- |
| 모든 BR에 `based_on`(STORY 또는 POLICY)이 하나 이상 있다. | 근거 정의 또는 BR 폐기 검토 |
| 모든 PR에 `based_on`(BR)이 하나 이상 있다. | 상위 BR 정의 또는 PR 폐기 검토 |
| PR의 `based_on`에 BR 외의 ID가 없다. | BR 경유로 수정 |
| `based_on`이 가리키는 ID가 실제로 존재한다. | ID 정정 또는 근거 정의 |
| 폐기된 ID를 `based_on`에서 참조하지 않는다. | 대체 근거로 교체 |
| 모든 STORY가 하나의 ACTOR를 표기하고, 그 ACTOR가 `05-역할.md`에 정의되어 있다. | Actor 정정 또는 정의 |
| 모든 PERSONA가 하나의 ACTOR에 종속되어 있다. | Actor 정정 또는 정의 |
| 어떤 BR에도 연결되지 않은 STORY·POLICY가 없다. | 아래 참고 |

어떤 BR에도 연결되지 않은 STORY·POLICY는 곧바로 오류로 보지 않는다. 현재 범위(Phase)의 요구가 아직 도출되지 않았거나 범위 밖 항목일 수 있으므로 PO가 도출 여부를 판단한다.

## 6. ID 변경 시 관계 유지

ID 스키마 §4·§5에서 통합·분리 시 기존 ID와의 추적 관계를 유지하도록 한 것을 다음과 같이 처리한다.

| 변경 유형 | 처리 |
| --- | --- |
| 표현 수정 (동일 목적 유지) | 기존 ID와 `based_on`을 유지한다. 근거가 바뀌었다면 `based_on`만 갱신한다. |
| 분리 | 유지 대상 ID와 신규 ID가 각각 필요한 근거만 `based_on`에 승계한다. 신규 항목의 `비고`에 분리 전 ID를 기재한다. |
| 통합 | 통합 후 ID가 통합 전 항목들의 `based_on`을 모두 승계한다. `비고`에 통합된 이전 ID를 기재한다. |
| 폐기 | 해당 ID를 `based_on`으로 참조하던 하위 항목을 찾아 대체 근거로 교체하거나, 근거가 없으면 하위 항목의 폐기 여부를 검토한다. 폐기 ID는 재사용하지 않는다. |

## 7. 변경 영향 분석

Business Context, 정책 또는 Requirement가 변경되면 변경된 항목에서 **하위 방향으로** 영향을 확인한다.

| 변경 대상 | 확인 대상 |
| --- | --- |
| `ACTOR-###` | 종속 `PERSONA-###`, 해당 Actor의 `STORY-###`, 이를 근거로 한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `PERSONA-###` | 이를 보조 참조한 `STORY-###`. 스토리의 목적이 바뀌는 경우에만 하위 BR·PR로 확대 |
| `STORY-###` | `based_on`에 해당 STORY를 포함한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `POLICY-###` | `based_on`에 해당 POLICY를 포함한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `BR-###` | `based_on`에 해당 BR을 포함한 `PR-###` |
| `PR-###` | 하위 추적 대상 없음. 동일 BR에서 파생된 다른 PR과의 정합성 확인 |
| Business Context 문서 | 문서 내용을 반영한 STORY·POLICY·BR을 확인 후 하위로 확대 |

### 영향 분석 절차

1. 변경 항목의 ID와 변경 내용을 특정한다.
2. `based_on`을 검색하여 해당 ID를 근거로 삼은 하위 항목을 모두 찾는다.
3. 각 하위 항목이 변경된 근거와 여전히 일치하는지 확인한다.
4. 일치하지 않는 항목은 수정 대상으로 정리하고 PO 확인을 거친다.
5. 수정된 항목이 있으면 다시 그 항목을 근거로 한 하위 항목까지 2~4를 반복한다.

변경 영향 분석은 AI Agent가 지원할 수 있으나, 수정 여부와 범위에 대한 최종 판단은 PO가 한다.

---

## 8. 미결 사항과의 관계

* 근거가 부족하거나 근거 간 충돌로 `based_on`을 확정할 수 없으면 해당 요구사항·스토리를 작성하지 않고 `BR/11-open issues.md`에 OI로 등록한다.
* 추적성 규칙 위반으로 발견된 확인 필요 사항도 동일하게 OI로 관리하며, 각 문서에 별도 목록을 작성하지 않는다.
* OI가 해소되면 결정된 내용을 해당 책임 문서에 반영하고 필요한 `based_on`을 기재한다.
