# 03. 범위 (Phase 1 MVP)

**목표:** 관리자가 고유번호를 등록하면 원장에 기록되고, 그 데이터로 플랫폼에 상품이 노출되며, 누구나 진위를 조회할 수 있다.

```
[관리자 등록/검수] → [원장 기록] → [플랫폼 상품(Asset) 활성화] → [유저 거래]
     Phase 1 ──────────────────────────────┘      └── Phase 2
```

## 설계 원칙

| # | 원칙 | 내용 |
|---|---|---|
| 1 | 원장 = 진실 원천 | 진위·소유는 원장, 가격·호가·결제 등 변동 데이터는 DB |
| 2 | Asset이 연결고리 | 원장에 기록(`CONFIRMED`)된 asset만 플랫폼에 노출 |
| 3 | 이벤트 append-only | Phase 1은 `REGISTERED`, Phase 2에서 `LISTED`/`SOLD`/`OWNERSHIP_TRANSFERRED` 추가 |
| 4 | 개인정보 미기록 | 고유번호는 해시(+salt)로 저장, 유저는 익명 ID만 사용 |

## In Scope

| 영역 | 기능 | 상세 |
|---|---|---|
| 관리자 | 로그인 | 단일 역할, 계정은 시드/수동 발급 |
| 관리자 | 상품 마스터 관리 | 브랜드, 모델, 이미지 등록 |
| 관리자 | 고유번호 등록 | 입력, 형식 검증, 중복 검사 (DB + 원장) |
| 관리자 | 원장 기록 요청/상태 | `PENDING → CONFIRMED / FAILED` 표시 |
| 관리자 | 실패 건 재시도 | 수동 재시도 |
| 관리자 | 등록 이력 조회 | 등록자, 시각, tx 해시 |
| 원장 | `REGISTERED` 이벤트 기록 | `serial_hash`, `product_id`, `registered_at` (개인정보 제외) |
| 원장 | tx 결과 저장 | tx 해시, 블록 확인 결과를 DB에 저장 |
| 원장 | 체인 어댑터 인터페이스 | `register()`, `verify()`, `getHistory()` / 구현체 1개, 교체 가능 구조 |
| 원장 | 운영 환경 | 테스트넷/개발망 한정 |
| 플랫폼 | 상품 목록/상세 | `CONFIRMED` asset만 노출, 읽기 전용, 로그인 불필요 |
| 플랫폼 | 고유번호 진위 조회 | 원장 대조 결과, 등록 시각, tx 링크 표시 |
| 플랫폼 | 상품 상태 | `REGISTERED` 구현, `LISTED`/`SOLD`는 스키마만 정의 |
| 공통 | 데이터 모델 | `asset`, `product`, `admin_user`, `ledger_tx` |
| 공통 | 조회 API 문서화 | |
| 공통 | 감사 로그 | 누가 무엇을 등록했는지 |

## 완료 기준 (Definition of Done)

| # | 기준 |
|---|---|
| 1 | 관리자가 고유번호를 등록하면 원장에 기록되고 DB에 tx 해시가 남는다 |
| 2 | 같은 고유번호는 재등록되지 않는다 |
| 3 | 일반 유저가 고유번호로 조회하면 원장 기준의 진위 결과가 나온다 |
| 4 | `CONFIRMED` 되지 않은 asset은 플랫폼에 노출되지 않는다 |
| 5 | 체인 어댑터만 교체해서 다른 체인으로 붙일 수 있다 |

## Phase 1 / Phase 2 비교

| 구분 | Phase 1 (MVP) | Phase 2 |
|---|---|---|
| 핵심 | 등록 → 원장 기록 → 노출/진위 조회 | 중개거래 플랫폼 완성 |
| 사용자 | 관리자, 비로그인 조회자 | 일반 유저, 협력사 |
| 원장 이벤트 | `REGISTERED` | + `LISTED`, `SOLD`, `OWNERSHIP_TRANSFERRED` |
| 거래 | 없음 (읽기 전용) | 입찰, 즉시구매, 에스크로, 정산 |
| 체인 환경 | 테스트넷 | 메인넷 |
