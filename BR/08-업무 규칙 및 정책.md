### 플랫폼 노출 조건의 해석

POLICY-002와 POLICY-010은 함께 읽는다. 등록 건은 두 가지를 모두 충족할 때만 플랫폼에 노출된다.

| 조건 | 기준 | 근거 |
| --- | --- | --- |
| 기록 상태 | 원장 기록 상태가 기록 완료여야 한다 | POLICY-002 |
| 등록 유효성 | 무효 처리되지 않아야 한다 | POLICY-010 |

기록 상태(원장 기록 처리의 진행 상태)와 등록 유효성(유효·무효)은 서로 다른 축이다. 기록 완료는 노출의 필요조건일 뿐이며, 기록 완료된 건이라도 무효 처리되면 노출에서 제외한다. 이 해석은 정책을 추가하거나 변경하지 않는다.

## 2. ID 스키마 및 넘버링 규칙

### 1. 목적

본 규칙은 블록체인 기반 정품 인증 서비스 Requirements Repository에서 추적 대상으로 관리하는 ID의 형식과 번호 부여 기준을 정의한다.

ID는 Repository에서 관리하는 산출물과 추적 대상 간의 추적성을 유지하기 위한 식별자로 사용한다.

각 문서에서는 ID 형식과 넘버링 규칙을 개별적으로 정의하지 않고 본 규칙을 따른다.

---

### 2. 공통 원칙

* 추적 대상으로 관리하는 항목에는 정의된 형식의 고유 ID를 부여한다.
* ID는 대상의 종류를 구분하는 ID 구분자와 순차 번호로 구성한다.
* 번호는 각 ID 유형별로 순차적으로 증가한다.
* 한 번 부여된 ID는 원칙적으로 변경하지 않는다.
* 삭제·폐기·종료된 ID는 새로운 항목에 재사용하지 않는다.
* 기존 항목 사이에 새로운 항목이 추가되더라도 기존 ID를 재번호화하지 않는다.
* 문서 이동, 파일명 변경, 목차 순서 변경 또는 상태 변경을 이유로 기존 ID를 변경하지 않는다.
* ID 자체에 상위·하위 관계나 업무 의미를 과도하게 포함하지 않는다.
* ID 번호 자체에 문서 또는 항목 간 관계를 포함하지 않는다.
* 문서 및 항목 간 관계와 추적 방법은 별도의 추적성 규칙을 따른다.

---

### 3. ID 유형

현재 Repository에서 사용하는 ID 유형은 다음과 같다.

| 대상                   | ID 구분자  | 형식            | 예시            |
| -------------------- | ------- | ------------- | ------------- |
| Business Requirement | BR      | `BR-###`      | `BR-001`      |
| Product Requirement  | PR      | `PR-###`      | `PR-001`      |
| Actor                | ACTOR   | `ACTOR-###`   | `ACTOR-001`   |
| Persona              | PERSONA | `PERSONA-###` | `PERSONA-001` |
| Open Issue           | OI      | `OI-###`      | `OI-001`      |
| Policy               | POLICY  | `POLICY-###`  | `POLICY-001`  |
| User Story           | STORY   | `STORY-###`   | `STORY-001`   |

`BR-###`는 개별 Business Requirement를 식별한다.

`PR-###`는 개별 Product Requirement를 식별한다.

`POLICY-###`는 정책 문서에 정의된 개별 정책 규칙(한 줄 단위)을 식별한다(상세 기준은 ID 스키마의 「12. Policy ID」 참조).

`STORY-###`는 고객여정에서 도출한 개별 유저 스토리를 식별한다(상세 기준은 ID 스키마의 「13. Story ID」 참조).

Repository의 추적성 뿌리는 `ACTOR-###`다. `PERSONA-###`는 정확히 하나의 `ACTOR-###`에 종속되는 하위 분류이며 추적성의 뿌리를 대체하지 않는다(상세 기준은 ID 스키마의 「11. Persona ID」 참조).

새로운 추적 대상에 ID가 필요한 경우 기존 ID 체계에 임의로 추가하지 않고 본 규칙에 ID 유형과 발급 기준을 먼저 정의한다.

### 4. Business Requirement ID

개별 Business Requirement는 다음 형식을 사용한다.

`BR-###`

예:

* `BR-001`
* `BR-002`
* `BR-003`

#### 번호 부여 기준

* Business Requirement 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 Business Requirement에는 현재 사용 중인 가장 큰 BR 번호의 다음 번호를 부여한다.
* Business Requirement가 삭제·폐기되더라도 해당 번호는 재사용하지 않는다.
* 내용이 수정되더라도 동일한 비즈니스 목적과 요구가 유지되는 경우 기존 ID를 유지한다.
* 하나의 Business Requirement가 서로 독립적인 여러 요구사항으로 분리되는 경우 기존 ID의 유지 대상을 판단하고 나머지 요구사항에는 신규 ID를 부여한다.
* 여러 Business Requirement가 하나로 통합되는 경우 기존 ID와의 추적 관계를 유지한다.
* 표시 순서가 변경되더라도 기존 ID를 재번호화하지 않는다.

### 5. Product Requirement ID

개별 Product Requirement는 다음 형식을 사용한다.

`PR-###`

예:

* `PR-001`
* `PR-002`
* `PR-003`

#### 번호 부여 기준

* Product Requirement 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 Product Requirement에는 현재 사용 중인 가장 큰 PR 번호의 다음 번호를 부여한다.
* Product Requirement가 삭제·폐기되더라도 해당 번호는 재사용하지 않는다.
* 내용이 수정되더라도 동일한 제품 요구와 목적이 유지되는 경우 기존 ID를 유지한다.
* 하나의 Product Requirement가 서로 독립적인 여러 요구사항으로 분리되는 경우 기존 ID의 유지 대상을 판단하고 나머지 요구사항에는 신규 ID를 부여한다.
* 여러 Product Requirement가 하나로 통합되는 경우 기존 ID와의 추적 관계를 유지한다.
* 표시 순서가 변경되더라도 기존 ID를 재번호화하지 않는다.

Business Requirement와 Product Requirement의 파생 및 연결 관계는 ID 번호 자체로 표현하지 않고 별도의 추적성 규칙을 따른다.

### 6. Actor ID

서비스 및 업무 과정에서 독립적인 역할을 수행하는 Actor는 다음 형식을 사용한다.

`ACTOR-###`

예:

* `ACTOR-001`
* `ACTOR-002`
* `ACTOR-003`

#### Actor 정의 및 관리 기준

Actor는 `05-역할 및 책임.md`에서 정의하고 `ACTOR-###` ID를 부여한다.

`04-이해관계자.md`는 고객, 내부 사용자, 외부 사용자 및 서비스 참여 주체를 식별하는 문서이며, 해당 문서에 정의된 대상이 자동으로 Actor가 되는 것은 아니다.

`04-이해관계자.md`에서 식별된 대상 중 서비스 또는 업무 과정에서 독립적인 책임과 행위를 수행하는 주체를 `05-역할 및 책임.md`에서 Actor로 정의한다.

고객의 가입·해지·자격 등 상태를 구분하기 위한 분류는 독립적인 행위 주체인지 확인한 후 Actor ID 부여 여부를 결정한다.

#### 번호 부여 기준

* Actor 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 Actor에는 현재 사용 중인 가장 큰 ACTOR 번호의 다음 번호를 부여한다.
* 동일 Actor에는 하나의 ID만 부여한다.
* 동일 Actor가 여러 고객여정 또는 Requirement에 참여하더라도 새로운 ID를 부여하지 않는다.
* Actor 명칭이 변경되더라도 동일 역할이 유지되는 경우 기존 ID를 유지한다.
* 기존 Actor의 역할이 실질적으로 분리되어 독립적인 Actor가 되는 경우 신규 ID를 부여한다.
* 삭제 또는 폐기된 Actor ID는 재사용하지 않는다.
* 표시 순서가 변경되더라도 기존 ID를 재번호화하지 않는다.

### 7. Open Issue ID

기획 문서 작성 과정에서 현재 확보된 근거만으로 확정할 수 없거나 추가 확인 또는 의사결정이 필요한 사항은 Open Issue로 관리하며 다음 형식을 사용한다.

`OI-###`

예:

* `OI-001`
* `OI-002`
* `OI-003`

#### 번호 부여 기준

* OI 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 OI에는 현재 사용 중인 가장 큰 OI 번호의 다음 번호를 부여한다.
* 동일한 미결 사항을 중복 생성하지 않는다.
* 해결 또는 폐기된 OI의 번호는 재사용하지 않는다.
* OI의 상태가 변경되어도 기존 ID를 유지한다.
* 관련 문서가 변경되더라도 동일한 미결 사항인 경우 기존 ID를 유지한다.
* 기존 OI 사이에 새로운 OI가 추가되더라도 기존 ID를 재번호화하지 않는다.

#### OI 생성 기준

기획 문서 작성 과정에서 다음과 같은 확인 필요 사항이 발생하면 OI로 등록한다.

* 원천자료만으로 사실을 확정할 수 없는 경우
* 서로 다른 원천자료의 내용이 충돌하는 경우
* 정책 또는 서비스 운영 기준에 대한 추가 확인이 필요한 경우
* 정책 또는 서비스 운영 기준에 대한 의사결정이 필요한 경우
* 고객, 이해관계자, Actor, 고객여정 등 기획 산출물을 확정하기 위해 추가 확인이 필요한 경우
* Business Requirement 또는 Product Requirement의 작성·확정을 위해 선행 확인이나 결정이 필요한 경우

#### OI 관리 기준

OI 관리 기준은 프로젝트 내 모든 기획 문서에 공통으로 적용한다.

어느 기획 문서에서든 확인 필요 사항이 발생하면 해당 문서에 직접 작성하지 않고 `15-open issues.md`에 OI로 등록한다.

모든 OI는 `15-open issues.md`에서 단일 관리한다.

`15-open issues.md`에서는 다음 정보를 관리한다.

* OI ID
* 미결 사항
* 관련 문서
* 상태

`관련 문서`에는 해당 미결 사항이 발생했거나 해결 결과가 반영되어야 하는 문서를 기록한다.

하나의 OI가 여러 문서에 영향을 미치는 경우 관련 문서를 함께 기록하고 동일한 OI를 중복 생성하지 않는다.

각 기획 문서에는 `확인 필요 사항`, `관련 미결 사항` 또는 OI 목록을 별도로 작성하지 않는다.

OI가 해결되면 확인 또는 결정된 내용의 관련 문서 반영과 해당 OI의 상태 변경은 `README.md`의 "GitHub 연동 파일 참조 및 수정 기준"에 따라 진행한다.

`15-open issues.md`는 다음 형식을 사용한다.

| ID     | 미결 사항 | 관련 문서     | 상태   |
| ------ | ----- | --------- | ---- |
| OI-### | 미결 사항 | `관련문서.md` | Open |

### 8. 파일 번호와 추적 ID의 관계

파일명의 번호와 추적 ID는 서로 다른 목적으로 사용한다.

예:

* `01-서비스개요.md`
* `02-서비스배경.md`
* `03-사업 범위 및 스코프 경계.md`
* `04-이해관계자.md`
* `05-역할 및 책임.md`
* `06-페르소나.md`
* `15-open issues.md`

파일명의 번호는 Repository 내 문서의 탐색 및 표시 순서를 의미한다.

반면 다음 ID는 추적 대상을 식별한다.

* `BR-001`
* `PR-001`
* `ACTOR-001`
* `OI-001`

따라서 파일 순서가 변경되더라도 추적 ID는 변경하지 않는다.

문서의 제목 번호(`#`, `## 1`, `### 1.1` 등)는 문서 구조를 나타내기 위한 것이며 추적 ID가 아니다.

---

### 9. ID 참조 원칙

ID를 가진 추적 대상을 다른 문서 또는 항목에서 참조하는 경우 가능한 한 대상의 명칭과 ID를 함께 사용한다.

예:

* `ACTOR-001` — 관리자
* `BR-012` — 고유번호 변환값 저장
* `PR-007` — 고유번호 단건 등록

ID는 항목의 위치나 문서 순서를 나타내기 위한 번호가 아니라 추적 대상을 식별하기 위한 값으로 사용한다.

구체적인 문서 및 항목 간 관계와 추적 방법은 별도의 추적성 규칙을 따른다.

---

### 10. 신규 ID 유형 추가

새로운 산출물 또는 추적 대상에 별도 ID가 필요한 경우 다음을 먼저 검토한다.

* 다른 문서 또는 Requirement에서 해당 대상을 지속적으로 참조해야 하는가?
* 변경 이력을 독립적으로 추적해야 하는가?
* 동일 유형의 항목이 여러 개 생성되는가?
* ID 없이 파일명 또는 제목만으로 관리할 경우 추적성이 저하되는가?

별도 ID가 필요하다고 판단되는 경우 본 문서에 다음 사항을 먼저 정의한 후 사용한다.

* ID 대상
* ID 구분자
* 형식
* 번호 부여 범위
* 재사용 여부
* 변경 시 ID 유지 기준
* 참조 방법

본 문서에 정의되지 않은 새로운 ID 구분자를 개별 문서에서 임의로 생성하지 않는다.

### 11. Persona ID

소비자를 서비스 이용 방식과 필요한 지원 수준에 따라 구분한 대표 페르소나는 다음 형식을 사용한다.

`PERSONA-###`

예:

* `PERSONA-001`
* `PERSONA-002`
* `PERSONA-003`

#### Persona 정의 및 관리 기준

Persona는 `06-페르소나.md`에서 정의하고 `PERSONA-###` ID를 부여한다.

Persona는 고객여정 작성 시 각 단계에서 참조할 대표 목표·Needs·Pain Point를 식별하기 위한 기준이며, 이후 고객여정 및 관련 Requirement에서 `PERSONA-###`로 참조한다.

#### Actor 종속 관계

Repository의 추적성 뿌리는 `ACTOR-###`이며, Persona는 Actor를 대체하지 않는다.

Persona는 정확히 하나의 `ACTOR-###`에 종속되는 하위 분류다. 하나의 Actor는 서비스 이용 방식·필요 지원 수준에 따라 여러 Persona로 세분화될 수 있다(Actor 1 : Persona N). 반대로 하나의 Persona가 여러 Actor에 걸쳐 정의되지는 않는다.

Persona 제목에는 대응하는 Actor ID를 함께 표기한다(예: "비대면 셀프처리형 고객 (PERSONA-001, ACTOR-001 대응)"). Actor가 아직 `05-역할 및 책임.md`(또는 해당 시점의 Actor 정의 문서)에 정의되지 않은 경우, Actor 확정 후 대응 관계를 반영한다.

고객여정 및 Business Requirement에서 구조적으로 추적하는 대상은 `ACTOR-###`이며, `PERSONA-###`는 해당 Actor의 이용 패턴·Pain Point를 설명하는 보조 참조로 사용한다.

#### 번호 부여 기준

* Persona 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 Persona에는 현재 사용 중인 가장 큰 PERSONA 번호의 다음 번호를 부여한다.
* 동일 Persona에는 하나의 ID만 부여한다.
* 동일 Persona가 여러 고객여정 또는 Requirement에 참여하더라도 새로운 ID를 부여하지 않는다.
* Persona 명칭이 변경되더라도 동일한 정의(목표·Needs)가 유지되는 경우 기존 ID를 유지한다.
* 기존 Persona의 정의가 실질적으로 분리되어 독립적인 Persona가 되는 경우 신규 ID를 부여한다.
* 삭제 또는 폐기된 Persona ID는 재사용하지 않는다.
* 표시 순서(문서 내 번호, 파일 순서)가 변경되더라도 기존 ID를 재번호화하지 않는다.

### 12. Policy ID

`BR/08-업무 규칙 및 정책.md`에서 정의하는 개별 정책 규칙은 다음 형식을 사용한다.

`POLICY-###`

예:

* `POLICY-001`
* `POLICY-002`
* `POLICY-003`

#### Policy 정의 및 관리 기준

* 정책 규칙 한 줄(하나의 허용·금지·조건·기준)마다 하나의 `POLICY-###`를 부여한다. 문서 내 구획 단위로 ID를 부여하지 않는다.
* 정책은 `BR/08-업무 규칙 및 정책.md` 하나의 문서에서 순번으로 관리한다.
* 하나의 규칙에는 하나의 정책 내용만 담는다. 서로 독립적인 내용은 별도의 `POLICY-###`로 분리한다.
* Business Requirement는 근거가 되는 정책을 `POLICY-###`로 참조한다.
* 확정되지 않은 정책은 정책 문서에 작성하지 않고 Open Issue(`OI-###`)로 관리한다.

#### 번호 부여 기준

* Policy 번호는 프로젝트 내에서 순차적으로 증가한다.
* 신규 정책 규칙에는 현재 사용 중인 가장 큰 POLICY 번호의 다음 번호를 부여한다.
* 규칙의 표현이 수정되더라도 동일한 정책 의도가 유지되는 경우 기존 ID를 유지한다.
* 하나의 규칙이 독립적인 여러 규칙으로 분리되는 경우 기존 ID의 유지 대상을 판단하고 나머지 규칙에는 신규 ID를 부여한다.
* 삭제 또는 폐기된 Policy ID는 재사용하지 않는다.
* 표시 순서(문서 내 순서, 파일 순서)가 변경되더라도 기존 ID를 재번호화하지 않는다.

### 13. Story ID

* `STORY-001`
* `STORY-002`

#### Story 정의 및 관리 기준

* Story 번호는 프로젝트 내에서 순차적으로 증가하며, 파일·폴더(Actor, Phase)가 달라도 하나의 순번으로 이어서 부여한다.

* 스토리의 표현이 수정되더라도 동일한 Actor의 동일한 목적이 유지되는 경우 기존 ID를 유지한다.
* 하나의 스토리가 독립적인 여러 스토리로 분리되는 경우 기존 ID의 유지 대상을 판단하고 나머지 스토리에는 신규 ID를 부여한다.
* 삭제 또는 폐기된 Story ID는 재사용하지 않는다.
* 표시 순서(문서 내 순서, 파일 순서)가 변경되더라도 기존 ID를 재번호화하지 않는다.

## 3. 추적성 규칙

### 1. 목적

본 규칙은 블록체인 기반 정품 인증 서비스 Requirements Repository에서 산출물과 추적 대상 간의 관계를 정의하고, 그 관계를 기록하는 방법(`based_on`)과 변경 영향을 확인하는 방법을 정의한다.

추적 대상의 ID 형식과 번호 부여 기준은 본 문서의 「2. ID 스키마 및 넘버링 규칙」을 따른다. 본 규칙은 ID 간의 **관계**만 다룬다.

---

### 2. 추적 체인

Repository의 추적성은 `ACTOR-###`를 뿌리로 하여 다음 순서로 파생된다.

화살표(↓)는 상위 근거에서 하위 산출물로 파생되는 방향이다.

```
         ACTOR
        ↓     ↓
  PERSONA     STORY      POLICY
 (종속 분류)     ↓          ↓
                └────┬─────┘
                     ↓
                     BR
                     ↓
                     PR
```

`PERSONA`는 `STORY`의 근거가 아니라 `STORY`가 선택적으로 참조하는 보조 자료이므로 다이어그램에서 `STORY`와 연결하지 않았다(표 3행 참조).

같은 내용을 파생 관계 목록으로 나타내면 다음과 같다. `A → B`는 "A를 근거로 B가 도출된다"는 뜻이며, `based_on`은 이 화살표의 반대 방향(B가 A를 가리킴)으로 기록한다.

| 순서 | 상위 근거 | → | 하위 산출물 |
| --- | --- | --- | --- |
| 1 | `ACTOR` | → | `PERSONA` |
| 2 | `ACTOR` | → | `STORY` |
| 3 | `PERSONA` | → | `STORY` (선택, 보조 참조) |
| 4 | `STORY` | → | `BR` |
| 5 | `POLICY` | → | `BR` |
| 6 | `BR` | → | `PR` |

| 대상 | ID | 정의 문서 |
| --- | --- | --- |
| Actor | `ACTOR-###` | `BR/05-역할 및 책임.md` |
| Persona | `PERSONA-###` | `BR/06-페르소나.md` |
| User Story | `STORY-###` | `BR/07-고객여정/{Actor}/04-유저스토리.md` |
| Policy | `POLICY-###` | `BR/08-업무 규칙 및 정책.md` |
| Business Requirement | `BR-###` | `BR/09-요구사항.md` |
| Product Requirement | `PR-###` | `PR/` |

고객 저니, 유저 시나리오, 유저 플로우는 추적 대상이 아니며(ID 스키마의 「13. Story ID」) 스토리를 도출하는 근거 자료로만 사용한다.

---

### 3. 관계 정의

관계는 **하위 항목이 상위 근거를 가리키는 단방향**으로만 기록한다.

| 하위 항목 | 상위 근거 | 필수 여부 | 기록 방식 |
| --- | --- | --- | --- |
| `PERSONA-###` | `ACTOR-###` 정확히 1개 | 필수 | Persona 제목에 Actor ID 표기(ID 스키마의 「11. Persona ID」) |
| `STORY-###` | `ACTOR-###` 정확히 1개 | 필수 | 스토리에 Actor ID 표기(ID 스키마의 「13. Story ID」) |
| `STORY-###` | `PERSONA-###` | 선택 | 이용 패턴·Pain Point를 설명하는 보조 참조 |
| `BR-###` | `STORY-###`, `POLICY-###` | 하나 이상 필수 | `based_on` |
| `PR-###` | `BR-###` | 하나 이상 필수 | `based_on` |

#### 관계 기준

* `POLICY-###`는 상위 추적 대상을 별도로 갖지 않는다. 정책의 근거는 정책 문서의 책임 범위에서 관리한다.
* BR은 STORY와 POLICY 중 하나 이상을 근거로 삼는다. 하나의 BR이 여러 STORY·POLICY를, 하나의 STORY·POLICY가 여러 BR을 근거로 연결될 수 있다(N:M).
* PR은 BR만 근거로 삼는다. PR이 `STORY-###` 또는 `POLICY-###`를 직접 참조하지 않는다. STORY·POLICY까지의 경로는 PR이 근거로 삼은 BR을 거쳐 확인한다.
* BR의 Actor는 근거로 삼은 STORY의 Actor로 확인한다. BR이 정책만을 근거로 하는 경우 Actor는 필요할 때 `based_on`에 `ACTOR-###`를 함께 기재한다.
* ID가 없는 Business Context 문서(서비스 개요, 서비스 배경, 범위, 이해관계자 등)는 `based_on` 대상이 아니다. 요구사항의 근거가 이 문서의 내용뿐이라면 해당 내용을 STORY 또는 POLICY로 먼저 정의한 후 참조한다.

---

### 4. `based_on` 사용 기준

* `based_on`은 **이 항목이 무엇에 근거해 도출되었는가**를 나타낸다.
* `based_on`은 하위 항목에만 기록한다. 상위 항목에는 하위 항목 목록(역참조)을 작성하지 않는다. 역방향 관계는 `based_on`을 검색하여 확인한다(중복 관리 방지).
* ID 번호나 문서 위치로 관계를 표현하지 않는다(ID 스키마의 「2. 공통 원칙」).
* 근거는 실제로 요구를 도출한 상위 항목만 기재한다. 관련성이 낮은 항목을 참고용으로 나열하지 않는다.
* 근거를 확인할 수 없는 항목은 작성하지 않고 Open Issue(`OI-###`)로 등록한다.

#### 표기 형식

`based_on`은 ID 스키마의 「9. ID 참조 원칙」에 따라 ID와 명칭을 함께 표기하고, 여러 개는 쉼표로 구분한다.

```
STORY-003 — 진위 조회 결과 확인, POLICY-005 — 조회 결과 유형
```

#### 기재 위치

BR과 PR은 다음 열을 가진 표로 관리한다.

| ID | 요구사항 | based_on | 비고 |
| --- | --- | --- | --- |
| BR-### | 요구사항 내용 | `STORY-###`, `POLICY-###` | |
| PR-### | 요구사항 내용 | `BR-###` | |

* `비고`에는 요구사항이 분리·통합된 경우에만 관련된 이전 ID를 기재한다(「3. 추적성 규칙」의 「6. ID 변경 시 관계 유지」 참조).
* PR이 여러 파일로 나뉘더라도 열 구성은 동일하게 유지한다.

---

### 5. 추적 완결성 기준

다음 항목을 추적성 검증의 기준으로 사용한다.

| 검증 항목 | 위반 시 조치 |
| --- | --- |
| 모든 BR에 `based_on`(STORY 또는 POLICY)이 하나 이상 있다. | 근거 정의 또는 BR 폐기 검토 |
| 모든 PR에 `based_on`(BR)이 하나 이상 있다. | 상위 BR 정의 또는 PR 폐기 검토 |
| PR의 `based_on`에 BR 외의 ID가 없다. | BR 경유로 수정 |
| `based_on`이 가리키는 ID가 실제로 존재한다. | ID 정정 또는 근거 정의 |
| 폐기된 ID를 `based_on`에서 참조하지 않는다. | 대체 근거로 교체 |
| 모든 STORY가 하나의 ACTOR를 표기하고, 그 ACTOR가 `05-역할 및 책임.md`에 정의되어 있다. | Actor 정정 또는 정의 |
| 모든 PERSONA가 하나의 ACTOR에 종속되어 있다. | Actor 정정 또는 정의 |
| 어떤 BR에도 연결되지 않은 STORY·POLICY가 없다. | 아래 참고 |

어떤 BR에도 연결되지 않은 STORY·POLICY는 곧바로 오류로 보지 않는다. 현재 범위(Phase)의 요구가 아직 도출되지 않았거나 범위 밖 항목일 수 있으므로 PO가 도출 여부를 판단한다.

### 6. ID 변경 시 관계 유지

ID 스키마의 「4. Business Requirement ID」·「5. Product Requirement ID」에서 통합·분리 시 기존 ID와의 추적 관계를 유지하도록 한 것을 다음과 같이 처리한다.

| 변경 유형 | 처리 |
| --- | --- |
| 표현 수정 (동일 목적 유지) | 기존 ID와 `based_on`을 유지한다. 근거가 바뀌었다면 `based_on`만 갱신한다. |
| 분리 | 유지 대상 ID와 신규 ID가 각각 필요한 근거만 `based_on`에 승계한다. 신규 항목의 `비고`에 분리 전 ID를 기재한다. |
| 통합 | 통합 후 ID가 통합 전 항목들의 `based_on`을 모두 승계한다. `비고`에 통합된 이전 ID를 기재한다. |
| 폐기 | 해당 ID를 `based_on`으로 참조하던 하위 항목을 찾아 대체 근거로 교체하거나, 근거가 없으면 하위 항목의 폐기 여부를 검토한다. 폐기 ID는 재사용하지 않는다. |

---

### 7. 변경 영향 분석

Business Context, 정책 또는 Requirement가 변경되면 변경된 항목에서 **하위 방향으로** 영향을 확인한다.

| 변경 대상 | 확인 대상 |
| --- | --- |
| `ACTOR-###` | 종속 `PERSONA-###`, 해당 Actor의 `STORY-###`, 이를 근거로 한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `PERSONA-###` | 이를 보조 참조한 `STORY-###`. 스토리의 목적이 바뀌는 경우에만 하위 BR·PR로 확대 |
| `STORY-###` | `based_on`에 해당 STORY를 포함한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `POLICY-###` | `based_on`에 해당 POLICY를 포함한 `BR-###`, 그 BR을 근거로 한 `PR-###` |
| `BR-###` | `based_on`에 해당 BR을 포함한 `PR-###` |
| `PR-###` | 하위 추적 대상 없음. 동일 BR에서 파생된 다른 PR과의 정합성 확인 |
| Business Context 문서 | 문서 내용을 반영한 STORY·POLICY·BR을 확인 후 하위로 확대 |

#### 영향 분석 절차

1. 변경 항목의 ID와 변경 내용을 특정한다.
2. `based_on`을 검색하여 해당 ID를 근거로 삼은 하위 항목을 모두 찾는다.
3. 각 하위 항목이 변경된 근거와 여전히 일치하는지 확인한다.
4. 일치하지 않는 항목은 수정 대상으로 정리하고 PO 확인을 거친다.
5. 수정된 항목이 있으면 다시 그 항목을 근거로 한 하위 항목까지 2~4를 반복한다.

변경 영향 분석은 AI Agent가 지원할 수 있으나, 수정 여부와 범위에 대한 최종 판단은 PO가 한다.

---

### 8. 미결 사항과의 관계

* 근거가 부족하거나 근거 간 충돌로 `based_on`을 확정할 수 없으면 해당 요구사항·스토리를 작성하지 않고 `BR/15-open issues.md`에 OI로 등록한다.
* 추적성 규칙 위반으로 발견된 확인 필요 사항도 동일하게 OI로 관리하며, 각 문서에 별도 목록을 작성하지 않는다.
* OI가 해소되면 결정된 내용의 해당 책임 문서 반영과 필요한 `based_on` 기재는 `README.md`의 "GitHub 연동 파일 참조 및 수정 기준"에 따라 진행한다.

## 4. 용어집

기획 문서에서 공통으로 쓰는 서비스 용어를 정의한다. 각 문서는 용어를 개별적으로 정의하지 않고 이 문서의 정의를 따른다. 용어에는 추적 ID를 부여하지 않는다.

### 1. 서비스 용어

| 용어 | 뜻 |
| --- | --- |
| 고유번호 | 제조사가 제품마다 발급한 고유한 인증 번호. 정품 여부를 확인하는 기준이 되며, 모든 등록 건의 식별자다. 서명 NFC 칩, QR 코드, 제품 표기 등 매체에 담을 수 있다 |
| 상품 마스터 | 고유번호를 연결할 상품의 기본 정보(브랜드, 모델, 이미지) |
| 등록 건 | 고유번호 하나를 상품에 연결해 등록한 단위 |
| 등록 근거 | 제품을 등록해도 된다고 판단하는 근거 자료. Phase 1은 신규 제품의 제조사 협력 자료를 말한다. 기존 제품의 영수증·전문가 감정 결과는 추후 검토한다 |
| 원장 | 고유번호 등록 사실을 위·변조할 수 없게 남기는 블록체인 기록. 진위 판단의 기준이다 |
| 원장 기록 | 등록 건의 등록 사실을 원장에 남기는 일 |
| 기록 번호 | 원장에 기록된 건마다 부여되는 고유한 확인 번호(tx 해시). 이 번호로 기록을 찾아 확인할 수 있다 |
| 플랫폼 노출 | 등록 건이 플랫폼의 조회 결과·상품 상세에 보이는 것. Phase 1은 목록 화면 없이 상세만 제공한다. 원장 기록이 완료되고 무효 처리되지 않은 건만 노출된다 |
| 무효 처리 | 잘못 등록된 등록 건에 '무효' 기록을 추가하는 일. 기존 등록 기록은 수정·삭제하지 않으며, 무효 처리된 건은 플랫폼 노출에서 제외된다 |
| 등록 유효성 | 등록 건이 유효한지 무효 처리되었는지를 나타내는 구분. 원장 기록 상태와는 별개다 |
| 일괄 등록 | 여러 건의 고유번호를 한 번에 등록하는 방식. 단건 입력과 함께 관리자가 사용한다 |
| 인증 칩 | 제품에 부착하는 서명 기능이 있는 보안 NFC 칩(Phase 1 등록 제품은 필수). UID로 식별하며, 스캔할 때마다 내부 비밀키로 동적 인증값을 생성하고 서버가 이를 검증해 진품 칩인지 확인한다. 칩은 제품에서 떼어 옮길 수 있으므로 칩 검증만으로 제품의 진위를 보증하지 않는다. 이 문서에서 '서명 검증'은 칩 인증 검증을 뜻한다 |
| 칩 인증정보 | 서버가 칩의 진위를 검증하는 데 필요한 정보(비밀키 등). 서비스에 반입해 서버 측에서 안전하게 관리하며 원장에 기록하거나 화면에 표시하지 않는다 (POLICY-020) |
| 동적 인증값 | 칩이 스캔할 때마다 생성하는 인증값. 제품에 연결하는 고정 정보가 아니며 서버의 칩 인증 검증에만 사용한다 |
| 칩 상태 | 칩의 사용 가능 여부를 나타내는 구분(활성, 폐기, 분실, 훼손 등). 활성이 아닌 칩은 '정품'으로 표시하지 않는다. 상태 값의 종류와 전환 규칙은 확정하지 않았다 |
| 칩 스캔 조회 | 소비자가 칩이 부착된 제품의 인증 칩을 스캔해 진위를 조회하는 방식. 칩 인증 검증, 칩에 연결된 등록 건과 칩 상태 확인, 원장 대조를 모두 통과하면 '정품'으로 표시한다 |
| 번호 직접 입력 조회 | 소비자가 고유번호를 입력해 조회하는 방식. 번호는 눈으로 보고 복사할 수 있어 제품정보 접근용으로만 제공하며, '정품' 표시나 실물 진위 판정을 하지 않는다 |
| QR 스캔 조회 | 소비자가 제품의 QR 코드를 스캔해 조회하는 방식. QR은 이미지로 복사할 수 있고 복사본도 같은 결과 화면을 열므로, 서명 검증이 없으면 번호 직접 입력 조회와 같이 제품정보 접근용으로만 제공하고 실물 진위를 판정하지 않는다 |
| 진위 조회 | 칩 스캔, QR 스캔, 고유번호 직접 입력으로 원장 기록과 대조해 결과를 보여 주는 기능의 통칭. 실물 진위를 판정하는 것은 칩 스캔뿐이며 결과 유형은 조회 방식에 따라 다르다(칩 스캔: 정품 / 무효 처리됨 / 미등록 / 정품 인증 실패 / 인증 중지된 칩 / 칩 확인 불가, 번호 입력·QR 스캔: 등록된 제품정보 / 무효 처리됨 / 조회 정보 없음) |
| 조회 횟수 | 고유번호별로 진위 조회가 이루어진 횟수. 관리자가 확인할 수 있다 |
| 등록 이력 | 등록 건별로 등록자, 등록 시각, 기록 번호를 확인할 수 있는 내역 |
| 작업 이력 | 누가 무엇을 했는지 남기는 기록. 등록 작업마다 남는다 |

### 2. 원장 기록 상태

등록 건의 원장 기록 진행 상태를 나타내는 값이다. 문서에서는 상태 이름으로 쓰고, 상태값은 필요한 경우에만 병기한다. 등록 유효성(유효·무효)은 이 상태와 별개이며, 플랫폼 노출은 기록 상태와 등록 유효성을 함께 본다.

| 상태 이름 | 상태값 | 뜻 | 플랫폼 노출 |
| --- | --- | --- | --- |
