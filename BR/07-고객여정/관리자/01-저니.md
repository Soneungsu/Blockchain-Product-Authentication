# 관리자 고객 저니 (ACTOR-001)

관리자(ACTOR-001)가 제품 고유번호를 등록하고 원장 기록 결과를 확인·관리하며, 오등록 건 처리와 조회 현황 확인까지 수행하는 과정을 단계별로 정리한다. 유저 시나리오·유저 플로우·유저 스토리를 도출하는 근거 자료이며 별도 ID는 부여하지 않는다(ID 스키마 §13). 용어(원장, 기록 번호, 기록 대기·기록 완료·기록 실패 등)는 `08-업무 규칙 및 정책.md`의 용어집를 따른다.

## 1. 저니 개요

| 항목 | 내용 |
| --- | --- |
| Actor | ACTOR-001 — 관리자 (대응 이해관계자: 운영사) |
| 페르소나 | PERSONA-001 — 등록 담당 운영자 |
| 범위 | Phase 1 (MVP). 관리자는 단일 역할이며 회원가입 없이 운영 측에서 미리 만들어 준 계정으로 이용한다 |
| 이용 환경 | 사무 환경, PC 관리자 페이지 |
| 여정 목표 | 오류 없이 빠르게 고유번호를 등록하고, 원장에 기록되었음을 확실하게 확인한다 |
| 시작 조건 | 운영 측에서 미리 만들어 준 관리자 계정을 보유하고 있다 |
| 종료 조건 | 등록한 고유번호가 기록 완료 상태이고, 등록 이력에서 근거(등록자·등록 시각·기록 번호)를 확인할 수 있다. 오등록 건은 무효 처리되어 플랫폼에 노출되지 않는다 |
| 관련 원칙 | 원장이 진위의 기준 / 기록 완료된 건만 플랫폼 노출(무효 처리된 건 제외) / 기록은 수정·삭제하지 않고 추가로만 남김 / 개인정보는 기록하지 않음 |

## 2. 단계 요약

```
① 로그인
↓
② 상품 마스터 준비
↓
③ 고유번호 입력·검증 (단건 / 일괄)
↓
④ 최종 확인 및 원장 기록 요청
↓
⑤ 원장 기록 결과 확인
↓
⑥ 실패 건 재시도 (기록 실패일 때만)
↓
⑦ 오등록 건 무효 처리 (오등록이 발견될 때만)
↓
⑧ 등록 이력·작업 이력 조회
↓
⑨ 조회 횟수 확인
```

⑥은 원장 기록이 실패한 경우, ⑦은 오등록이 발견된 경우에만 발생하는 조건부 단계다. ①~⑤가 한 번의 등록 사이클을 이루며, 담당 운영자는 ③~⑤를 반복한다. ⑧·⑨는 등록과 별개로 필요할 때 수행한다.

## 3. 단계별 저니

### ① 로그인

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 허가된 계정으로 관리자 페이지에 진입한다 |
| 행동 | 관리자 페이지에 접속하여 받은 계정으로 로그인한다 |
| 접점 | 관리자 로그인 화면 |
| 시스템 반응 | 인증에 성공하면 관리 기능을 쓸 수 있고, 실패하면 쓸 수 없다 |
| 생각 | "내 계정으로 바로 들어가서 등록 작업을 시작하고 싶다" |
| 감정 | 중립 |
| Pain Point | 가입 기능이 없어 계정을 별도로 받아야 한다 |
| 기회 | 로그인 직후 등록 작업으로 바로 이어지는 동선 |

### ② 상품 마스터 준비

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 고유번호를 연결할 상품(브랜드·모델·이미지)을 준비한다 |
| 행동 | 등록하려는 제품의 상품 마스터가 있는지 확인하고, 없으면 브랜드·모델·이미지를 등록한다. 원장 기록에 연결되기 전의 상품 마스터는 수정·삭제할 수 있다 |
| 접점 | 상품 마스터 관리 화면 |
| 시스템 반응 | 상품 마스터를 저장하고, 이후 고유번호 등록 때 연결할 상품으로 고를 수 있게 한다. 원장 기록이 연결된(등록 완료된) 상품 마스터는 수정·삭제를 허용하지 않는다 |
| 생각 | "번호를 넣기 전에 이 제품이 어떤 상품인지 먼저 갖춰 놓아야 한다" |
| 감정 | 중립 |
| Pain Point | 상품 정보가 잘못 등록되면 이후 플랫폼에 보이는 정보에 그대로 반영되고, 등록이 완료된 뒤에는 고칠 수 없다는 부담 |
| 기회 | 등록 시점에 상품 정보를 바로 확인하게 하여 선택 실수를 줄임 |

### ③ 고유번호 입력·검증

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 고유번호를 정확하게 입력하고 등록 가능 여부를 즉시 확인한다 |
| 행동 | 파트너가 제공한 등록 근거(제조사 협력 자료 등)를 확인한 제품에 대해, 상품을 선택하고 제품 고유번호를 한 건씩 입력하거나 여러 건을 일괄 등록한다 |
| 접점 | 고유번호 등록 화면 |
| 시스템 반응 | 번호 형식을 확인하고(브랜드/상품별로 형식이 다를 수 있어 최소 검증만 수행), 이미 등록된 번호인지 서비스 내 등록 내역과 원장 양쪽에서 검사한다. 검사를 통과해야 최종 확인 단계로 넘어간다 |
| 생각 | "잘못된 형식이나 이미 등록된 번호는 여기서 바로 걸러졌으면 좋겠다" |
| 감정 | 긴장 (형식에 맞는 오입력은 이 단계에서 걸러지지 않는다는 부담) |
| Pain Point | 형식과 중복 검사만으로는 형식에 맞게 잘못 입력한 번호를 찾을 수 없다. 여러 건을 반복해서 입력하는 부담이 크다 |
| 기회 | 형식 오류·중복을 기록 요청 전에 즉시 막고 사유를 분명히 안내. 일괄 등록으로 반복 입력 부담 완화 |

### ④ 최종 확인 및 원장 기록 요청

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 원장에 남기기 전에 등록 내용이 맞는지 마지막으로 확인한다 |
| 행동 | 최종 확인 화면에서 상품과 고유번호 등 등록 내용을 확인하고 원장 기록을 요청한다 |
| 접점 | 최종 확인 화면 |
| 시스템 반응 | 관리자가 확인하고 요청한 건에 한해 원장에 기록을 요청하고 기록 대기로 표시한다. 이 화면 외의 추가 오입력 방지 수단(이중 입력 등)은 두지 않는다 |
| 생각 | "한번 기록되면 고칠 수 없으니 여기서 마지막으로 눈으로 확인해야 한다" |
| 감정 | 긴장 |
| Pain Point | 형식에 맞는 오입력은 관리자의 눈으로만 걸러진다 |
| 기회 | 등록 내용을 한눈에 대조할 수 있는 확인 화면 |

### ⑤ 원장 기록 결과 확인

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 등록한 번호가 원장에 실제로 기록되었음을 확실하게 확인한다 |
| 행동 | 기록 상태(기록 대기 → 기록 완료 / 기록 실패)와 기록 번호를 확인한다 |
| 접점 | 기록 상태 표시, 기록 번호 |
| 시스템 반응 | 기록 결과와 확정 결과를 저장해 상태로 보여 준다. 기록 완료가 되면 해당 건은 플랫폼에 노출될 수 있게 된다(무효 처리된 건은 제외) |
| 생각 | "성공했는지 실패했는지 애매하지 않게 알고 싶다" |
| 감정 | 기대 → 안도(기록 완료) / 불안(기록 실패, 지연) |
| Pain Point | 기록이 늦어지거나 실패했을 때 원인을 알기 어렵다 |
| 기회 | 상태를 분명히 구분해 보여 주고, 기록 번호로 근거를 제공 |

### ⑥ 실패 건 재시도 (조건부)

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 기록에 실패한 건을 다시 처리하여 등록을 완료한다 |
| 행동 | 기록 실패 건을 골라 직접 재시도하고 결과를 다시 확인한다. 재시도 횟수에는 제한이 없다 |
| 접점 | 실패 건 재시도 기능 |
| 시스템 반응 | 원장에 기록을 다시 요청하고 결과 상태를 갱신한다 |
| 생각 | "처음부터 다시 입력하지 않고 바로 다시 시도하고 싶다" |
| 감정 | 불안 → 안도 |
| Pain Point | 실패 원인을 모른 채 재시도해야 하는 막막함 |
| 기회 | 실패 건을 한곳에서 바로 재시도 |

### ⑦ 오등록 건 무효 처리 (조건부)

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 잘못 등록된 고유번호가 플랫폼에서 정상 건으로 보이지 않게 한다 |
| 행동 | 오등록된 건을 찾아 무효 처리를 요청한다 |
| 접점 | 등록 이력 화면, 무효 처리 기능 |
| 시스템 반응 | 기존 등록 기록은 수정·삭제하지 않고 '무효' 기록을 추가한다. 무효 처리된 건은 플랫폼 노출에서 제외한다 |
| 생각 | "이미 기록된 번호는 고칠 수 없으니, 잘못된 건은 무효로 남겨 노출되지 않게 해야 한다" |
| 감정 | 불안 → 안도 |
| Pain Point | 잘못 등록한 기록 자체는 지울 수 없다 |
| 기회 | 무효 처리 결과와 근거를 이력에서 바로 확인 |

### ⑧ 등록 이력·작업 이력 조회

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 누가 언제 무엇을 등록·처리했고 원장에 어떻게 기록되었는지 나중에 확인한다 |
| 행동 | 고유번호, 상품명, 등록자, 기간으로 검색·필터하여 등록 이력을 찾고, 등록자·등록 시각·기록 번호를 확인한다. 등록·무효 처리 등 관리자 작업 이력도 함께 확인한다 |
| 접점 | 등록 이력 화면, 작업 이력 화면 |
| 시스템 반응 | 조건에 맞는 등록 이력과 기록 결과를 보여 준다. 등록·무효 처리 등 작업마다 누가 무엇을 했는지 작업 이력으로 남는다 |
| 생각 | "나중에 이 번호가 언제 누구에 의해 등록됐는지 바로 찾을 수 있어야 한다" |
| 감정 | 중립 → 확신 |
| Pain Point | 이력이 흩어져 있으면 등록 근거를 확인하기 어렵다 |
| 기회 | 등록 결과와 근거를 한 화면에서 확인 |

### ⑨ 조회 횟수 확인

| 항목 | 내용 |
| --- | --- |
| 관리자 목표 | 고유번호별 진위 조회 횟수를 확인해 조회 현황을 파악한다 |
| 행동 | 고유번호별 진위 조회 횟수를 확인한다 |
| 접점 | 조회 횟수 확인 화면 |
| 시스템 반응 | 고유번호별 진위 조회 횟수를 기록해 보여 준다. 알림·통계 대시보드와 자동 탐지 기능은 제공하지 않는다 |
| 생각 | "조회 횟수가 유독 많은 번호가 있는지 직접 확인하고 싶다" |
| 감정 | 중립 |
| Pain Point | 조회 현황을 직접 찾아봐야 한다 |
| 기회 | 고유번호별 횟수를 한곳에서 확인 |

## 4. 감정 흐름

| 단계 | ① 로그인 | ② 상품 마스터 | ③ 입력·검증 | ④ 최종 확인·요청 | ⑤ 기록 확인 | ⑥ 재시도 | ⑦ 무효 처리 | ⑧ 이력 조회 | ⑨ 조회 횟수 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 감정 | 중립 | 중립 | 긴장 | 긴장 | 기대→안도 / 불안 | 불안→안도 | 불안→안도 | 확신 | 중립 |

감정이 가장 낮아지는 지점은 ③·④(오입력 부담)와 ⑤·⑥(기록 지연·실패)이며, PERSONA-001의 Pain Point와 일치한다.

## 5. 페르소나 연결

| PERSONA-001 항목 | 저니에서 확인되는 단계 |
| --- | --- |
| 목표: 오류 없이 빠르게 등록 | ③, ④ |
| 목표: 원장 기록 확실히 확인 | ⑤, ⑧ |
| Needs: 중복 번호 즉시 걸러짐 | ③ |
| Needs: 반복 등록 부담이 적을 것 | ③ (일괄 등록) |
| Needs: 등록 전에 내용을 최종 확인할 것 | ④ |
| Needs: 기록 성공 여부 명확 | ⑤ |
| Needs: 실패 건 바로 재시도 | ⑥ |
| Needs: 오등록 건을 노출되지 않게 처리할 것 | ⑦ |
| Pain Point: 오입력 정정 부담 | ③, ④, ⑦ |
| Pain Point: 지연·실패 원인 파악 어려움 | ⑤, ⑥ |

⑨ 조회 횟수 확인은 PERSONA-001 항목이 아닌 정책(POLICY-011)에 근거한 업무이며, 페르소나와 직접 대응하지 않는다.
